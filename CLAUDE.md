# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Daniele Bartorilla — Fotografia Naturalistica" — a single-page bird photography gallery (Vite + React 19), deployed to GitHub Pages by CI. All website text is in Italian; code, comments, and error messages are in English. No tests, no linter, no TypeScript; styling lives in `src/index.css` (design tokens as CSS variables, class-based styles) plus `src/lightbox.css`. The site has a light and a dark theme — see "Theming" below. Fonts (Cormorant Garamond + Inter) are self-hosted as woff2 under `public/fonts/`, preloaded in `index.html`. Page-view analytics via Umami (script tag in `index.html`), cookie-free — see `src/Policies.jsx`.

The main page is: hero (the `hero: true` photo as background, in-page nav), "Scatto della settimana", gallery (responsive masonry with hover captions, species + year filter chips), "Chi sono" section, "Contatti" section, footer. Two further routes hang off the nav: `/specie` (species index) and `/numeri` (stats from the EXIF data). The masonry columns are assigned in JS by greedy shortest-column packing (`distributeIntoColumns` in `Gallery.jsx`: each photo goes to whichever column has the least accumulated height so far, estimated from its aspect ratio; 3 columns above 1000px / 2 below, mirrored by CSS flex on `.gallery-grid`/`.gallery-column`, `align-items: flex-start` so flex doesn't stretch shorter columns to match the tallest), not via CSS `column-count`: since gallery order is shooting date (most recent first), a CSS-columns layout would fill column 1 top-to-bottom before starting column 2, burying recent photos instead of spreading them across the top row. A frosted-glass sticky nav (with back-to-top and scroll progress) appears once the hero is scrolled past; on mobile the nav links collapse into a hamburger that opens a side `NavDrawer`. The about-section portrait is optional: drop `src/profile.jpg` (or `.jpeg`/`.png`) and it is picked up via `import.meta.glob`; a placeholder shows otherwise. In-page nav must scroll programmatically (`scrollIntoView`), not via `#anchor` links, which would clash with the hash router.

## Commands

- `npm run dev` — start dev server on port 3000 (runs `generate-photos.js` first).
- `npm run build` — runs `node src/generate-photos.js`, `vite build`, then `node src/generate-static-pages.mjs` (post-build: the static HTML surface, see below).
- Deploy is automatic: every push to `main` triggers `.github/workflows/deploy.yml`, which builds and force-pushes `dist/` as a single orphan commit to the `deploy` branch (the GitHub Pages source for https://danibart.it). There is no manual deploy script.

## Photo pipeline (the key architecture)

Source JPGs live in `photos/` (committed). `src/generate-photos.js` uses sharp to produce `generated_photos/fullsize/` (quality 90 mozjpeg, progressive), `generated_photos/slides/` (1280px and 2048px renditions, `<name>-<width>.jpg` — combined with the fullsize into a per-slide `srcSet` in `photos.jsx` so the lightbox downloads a right-sized file instead of the multi-MB fullsize; the `slides` array in `Gallery.jsx` is built by a module-scope `toSlide` and memoized on the filtered photo list, because a new array identity mid-swipe makes yarl reset its state — it must change only when the filters do), `generated_photos/original/` (quality 100 mozjpeg — opened in a new tab by the lightbox HQ button; re-encoded rather than copied so EXIF/GPS stays stripped), `generated_photos/thumbnails/` (600px wide, jpg + webp + avif — gallery `<picture>` prefers avif, then webp), `generated_photos/hero/` (1920px wide, jpg + webp + avif, only for `hero: true` entries), `generated_photos/social/` (1200px wide, for the static pages and Open Graph), and `generated_photos/metadata.json` (per photo: pixel dimensions, a tiny base64 blur-up placeholder used by the gallery and hero, the shooting date parsed from EXIF `DateTimeOriginal`/`DateTime` — used only to order the gallery, `null` if absent — and the rest of the shooting data parsed from EXIF via exif-reader — shown in the lightbox caption). `generated_photos/` is gitignored — it must be regenerated locally, and the app fails to show photos without it.

`photos.json` (repo root) is the single manifest: an array of `{filename, title, species, description}` entries (`species` is the optional Latin name, shown in the hover caption and lightbox; `description` may be empty and shows in the lightbox caption when set). Array order is gallery display order, but it's not hand-maintained: every run of `generate-photos.js` re-sorts it by each photo's EXIF shooting date, most recent first (undated photos keep their relative order and sort last), rewriting the file if the order changed. That same shooting date backs a "Nuova" glass badge on thumbnails less than 20 days old (`GalleryItem` in `Gallery.jsx`, computed client-side against `Date.now()` so it fades out on its own between deploys). One entry may carry `"hero": true` to become the hero background (falls back to the first entry). Alternatively, `"heroSmall": true` and `"heroLarge": true` (on different entries) pick distinct hero backgrounds for narrow vs wide viewports — the split happens at `(min-width: 1024px)` (`HERO_LARGE_QUERY` in `Gallery.jsx`, mirrored by the preload media queries in `generate-static-pages.mjs`); a missing variant falls back to the `hero: true` entry, then the first entry. The `heroLarge` photo also backs the site-wide Open Graph image. `src/photos.jsx` imports it and resolves URLs via `import.meta.glob`. **Adding a photo requires two steps:** drop the `.jpg` in `photos/` AND add an entry to `photos.json`. Each photo gets a stable URL id (URL-safe slug of `title` + MD5 of the filename), computed by `src/photo-id.mjs` — the single shared implementation; changing it breaks previously shared `/p/<id>/` links.

## Theming

Colours come in pairs: `:root` in `src/index.css` holds the dark palette as raw channels (`--bg-rgb`, `--text-rgb`, …) plus the solid tokens derived from them (`--bg: rgb(var(--bg-rgb))`). A theme therefore only restates the six channel lines and the solid tokens re-resolve. Anything needing transparency writes `rgb(var(--x-rgb) / 0.3)` — **no bare `rgba()` with literal channels**, or it will not follow the theme.

- **Three states, two stored.** No stored preference means "follow the device", handled purely by `@media (prefers-color-scheme: light)`. The sun/moon toggle pins `data-theme` on `<html>` and writes `theme` into localStorage; picking the theme the device already uses *clears* the override instead of pinning it. `src/theme.mjs` owns this, and `index.html` carries a copy of the read half as a pre-paint inline script so an overridden page never flashes the wrong theme. `generate-static-pages.mjs` inlines its own copy (`THEME_BOOT` / `THEME_SCRIPT`) because the static pages load no bundle.
- **The light palette is written twice** (once under `:root[data-theme="light"]`, once inside the media query). Plain CSS cannot share one block between the two, and `light-dark()` needs Safari 17.5 while `cssTarget` is still safari15.
- **Anything painted on a photograph keeps the dark colours in both themes** — the hero content and nav, the gallery caption, the "Nuova" badge, the featured text, and the whole lightbox. What they contrast with is the photo, not the page. That rule restates the channel tokens *and* `color`: headings inside those containers declare no colour of their own, so they inherit the value already resolved on `<body>` and overriding the tokens alone never reaches them.
- The hero overlay is split for the same reason: the scrim that darkens the photo under the title is a constant dark, and only the fade joining the hero to the page below follows the theme. That join is a `--hero-join` custom property so the media query can swap it alone — eased over ~22% of the hero for `heroLarge`, ~38% below the 1024px breakpoint, where a short ramp banded visibly. The query mirrors `HERO_LARGE_QUERY` in `Gallery.jsx`.
- The light accent is a deeper bronze (`122 92 34`) — the dark theme's gold reaches only 1.9:1 on a light background.
- The Cookie Policy documents the localStorage entry. If theme storage changes, that page has to change with it.

## Static HTML surface

The SPA renders entirely in JS, so everything a crawler or a link preview needs is emitted as plain HTML by `src/generate-static-pages.mjs` (run by `build` after vite): `dist/p/<id>/index.html` per photo (the photo, its species, description and shooting data, `ImageObject` JSON-LD, prev/next links, and a CTA into the gallery), `dist/s/<slug>/index.html` per species plus `dist/s/` as their index, and `dist/sitemap.xml` listing all of them. It also injects the site-wide Open Graph tags, the gallery JSON-LD and the hero preload into `dist/index.html`.

Two things to know before touching it:

- **The `/p/` pages are real pages, not redirects.** They used to bounce into the SPA deep link; a redirect is not indexable, and the static page paints the photo without the JS bundle. The lightbox share button still hands out these URLs (in dev, where they don't exist, it falls back to `/#/?photo=<id>`). Each gallery thumbnail also carries a real `<a href>` to its `/p/` page (`.gallery-link`, a transparent overlay that intercepts plain clicks to open the lightbox) — that anchor is the only path a crawler has from the home page into the photo pages.
- **Page titles are deduplicated, not templated.** Five photos are titled "Airone Cenerino"; `buildPageTitles` escalates a colliding group through progressively more specific labels (bare title → + date → + time → "n di m") until it breaks up, so unique titles stay plain and only real clashes get qualified. The last level is unique by construction — burst frames tie on everything else.
- **The Open Graph copy is published under a descriptive filename** (`social/airone-cenerino-<id>.jpg`, not `IMG_5893.jpg`), since the filename is one of the signals Google Images reads.
- **Hashed assets are matched by byte size.** vite flattens every rendition into `dist/assets/<basename>-<hash>.<ext>`, so a photo's thumbnail, full-size copy and quality-100 original all collide as `IMG_6501-<hash>.jpg`. `assetFor("fullsize/IMG_6501.jpg")` narrows by name prefix and then matches the exact file size against the source in `generated_photos/` — vite copies assets byte for byte. Do not try to parse the hash out of the filename: vite's hash alphabet includes `-`, so `IMG_6501-1280-<hash>.jpg` cannot be split back into stem and hash by pattern. A miss warns, except below vite's 4096-byte `assetsInlineLimit`, where the asset legitimately became a data URI in the bundle.
- **The `/p/` page is the lightbox's HQ destination**, so it serves the photo full-resolution: the `srcSet` tops out at the `fullsize` rendition and `sizes="100vw"` lets a retina or wide screen pick it. The frame's shape comes from an inline `aspect-ratio` plus a `max-width` capping it to 78vh, both computed at build time — the img cannot size the box itself before a multi-MB file arrives, and without it the page collapsed and jumped on load. The blurred `::before` under it is the same base64 placeholder the gallery uses.

`src/species.mjs` is the shared source of truth for species naming — Latin→Italian common names, the `·` splitting for multi-species entries, and the `/s/<slug>/` slugs — imported by both the React app and the generator. Like `photo-id.mjs`, renaming a species there breaks its existing URL.

`src/generate-photos.js` (run by both `dev` and `build`) reconciles `photos/*.jpg` with `photos.json`: a `.jpg` with no manifest entry aborts with a nonzero exit (the entry needs hand-written title/species), while a manifest entry whose `.jpg` was deleted is pruned from `photos.json` automatically — removing a photo only takes deleting the file. Generation is incremental (skips existing outputs) and deletes stale outputs whose source photo was removed.
## Routing / lightbox

`App.jsx` uses a hash router (GitHub Pages compatibility): `/` renders `Gallery.jsx`, `/specie` the species index, `/numeri` the stats page (both wrapped in `src/SubPage.jsx`, which resets the scroll on mount), `/privacy` and `/cookie` the legal pages in `src/Policies.jsx`. The footer lives outside `RouterProvider`, so its links are plain `#/...` hash links rather than `<Link>`.

The gallery keeps all of its state in the query string — `?photo=<id>` for the lightbox, `?specie=<slug>` and `?anno=<year>` for the filters — so every view is linkable and there is no state/URL sync to maintain. Anything that navigates goes through `navigateWithParams`, which *merges* into the existing query string; replacing it outright would drop the filters on a swipe (or the open photo on a filter click). That helper reads the location from a ref rather than a dependency: it is passed to the memoized `GalleryItem`s, and a fresh identity per swipe would re-render all of them. The lightbox walks the *filtered* list, so arrowing out of a filter can't land on another species; a deep link to a photo the filters exclude falls back to the full list.

Plugins in use: Zoom, Thumbnails, Slideshow. yarl's labels are English by default, so the Italian ones are passed via `labels`. Toolbar buttons are a custom array — the `"slideshow"` string is a placeholder the plugin substitutes in place, and without it the button would be prepended instead. The Zoom plugin is kept for pinch/double-tap/wheel but its `+`/`−` buttons are dropped with `render.buttonZoom: () => null`. The lightbox is deliberately bare: no captions, no counter, no info button — just the photo, the filmstrip and slideshow / HQ / share / close. The HQ button leaves the SPA for the photo's `/p/` page (in dev, where those do not exist, it opens the quality-100 rendition instead).
